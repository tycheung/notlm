# ADR-002 — Host project folder + config-only packs (JSON)

## Status

Accepted

## Context

When the assistant is installed into an arbitrary codebase, scans, drafts, checklists, and the live pack must be easy for developers to find, review, and version. Generating TypeScript registries (`guideIds.ts`, binder modules) spreads “learnings” into code and fights the product goal of a plug-and-play config layer.

## Decision

1. **Single project root folder** (default name **`.uipilot/`**, overridable via `UIPILOT_HOME` / `uipilot.config.json` → `"root"`). All scan outputs, drafts, checklists, traces, and the accepted pack live **only** under this folder.
2. **Pack = JSON configuration only** for v1 learnings. After scan / structured extract / LLM author, the system writes/updates a **small fixed set of JSON files** — not application TypeScript.
3. **Runtime loads JSON** (import assertion, `fs` in Node tools, or bundler `?url` / fetch). Core evaluates declarative binders from JSON; the host supplies only a thin `getContext()` that fills a data bag — **not** per-step hand-written completeness modules generated by us.
4. **Secrets stay out of the folder** (or in gitignored `*.local.json`). LLM keys remain env / user config.
5. **Codegen that emits TS is non-goals for v1 learnings.** Optional human-facing `checklist.json` / markdown listing “add these `data-guide-id`s” is fine; no required `guideIds.ts` generation.

## Standard layout (host repo)

```text
.uipilot/
  config.json              # features, guideAttr, paths, author defaults (no secrets)
  inventory.json           # last Playwright/control crawl
  structured-draft.json    # mechanical dag generate output
  checklist.json           # open gaps (binders, unmapped controls, low-confidence edges)
  pack/
    manifest.json          # id, version, title, features, file refs (or inline)
    flow.json              # steps DAG
    controls.json          # guide ids, roles, step links, nav hints
    intents.json           # aliases, meta, slot schemas
    binders.json           # declarative completeness predicates
    corpus.json            # NLU cases
    glossary.json          # optional
  drafts/                  # LLM/author proposals before accept
    <timestamp>/
      …
  traces/                  # optional record-mode ActionTrace JSON
```

Minimal “few files” mental model for most apps: **`config.json` + `inventory.json` + `checklist.json` + `pack/*.json`**.

## Consequences

- Schema epic defines JSON Schema for each file; `uipilotCLI pack validate` checks the folder.
- Completeness language must be expressive enough in JSON (path + op + value, all/any groups) — ADR or schema slice locks the binder DSL.
- Host still annotates real UI with `data-guide-id` (that is product code, not generated learnings).
- This monorepo’s `packs/demo-todo` should migrate to the same JSON shape for parity.
